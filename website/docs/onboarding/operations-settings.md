# Operations Settings

<Lead>The Operations step in the Market Onboarding UI sets how a market runs from day to day: when its payments execute, how long a customer can cancel, and how hard Billpay should push to meet a cutoff. Each setting drives something specific at runtime.</Lead>

None of these settings is a code change. They travel in the market's release like the rest of its profile, and they take effect when that release is activated.

| Setting | Used by | What it controls |
| --- | --- | --- |
| Time zone and execution time | That account type's scheduled-payments Schedule | When the due payments of the market and account type start executing. Each release sets `timeZone`, an IANA zone such as `America/Phoenix`, and `executionTime`, `HH:mm`, local midnight when unset, so account types in one market can run at different times (agreed 2026-11-07). The Schedule takes the time zone, so the execution time holds across daylight saving. The US runs at 00:01 on Phoenix time (MST), which has no daylight saving |
| Cancellation window | Cancel and update | How long a customer can still change or cancel a scheduled payment: `cancellationWindow`, an ISO duration before the run, by default `PT1H`, so it closes at 11 PM local time before a midnight run (agreed 2026-11-07). The cutoff is stored with the payment when it is scheduled, so a later release doesn't move it (Proposed). A late request gets 409. A corporate payment closes sooner if its allocations are requested first |
| Cutoff, if any | The governor's cutoff floor and alert | The time the market's execution must finish by. SEPA markets have a cutoff of three to four hours; the US has none |
| Allocation fetch timing and alert point | The `ALLOC_REQUEST` due time, and the late-allocation alert | When to ask for a scheduled corporate payment's allocations: `allocationFetchBefore`, an ISO duration before the execution time on the due date, `PT0S` by default (at the execution time), `P1D` a day before or `PT6H` six hours before. When to raise an alert if they haven't arrived: `allocationAlertAfter`, an ISO duration counted from when the payment turned `ALLOCATING`; a release without it raises no late alert (agreed 2026-11-08). The request also ends cancel and update for that payment |
| Representment rules | The return workflow's judgment, and the representment date | The release's `representment` block: `representableReasons`, `maxRepresentments`, and `delayDays`, the days after the return arrives, 0 for the same day. A release without the block represents nothing (agreed 2026-11-07) |
| Raven notifications | Every stage's announcement | Which status changes send the customer a Raven message. By default `SCHEDULED`, `DECLINED`, `CANCELLED`, `PROCESSED` and `RETURNED`. A market can change the default, and an account type can change its market's. Where both have a setting, the account type's wins. A status that is switched off sends no message, and Fulfil then waits for RTF alone. Its key is `ravenStatuses`, a list of statuses in each market and account type's release, or in an extension of it later. A market-wide list is set in each of its account types' releases, and with no key the default list applies (agreed 2026-11-08) |
| Bank confirmation wait | The waiting workflow's timer | How long a Pay with Bank Transfer payment waits for a confirm, from the channel or Amex Pay with Bank Transfer, or for M3's settled notice: `bankConfirmation.confirmationWindow`, set per market, 24 to 48 hours. A payment with neither once the wait and a 10-second grace have passed is `DECLINED` with `CONFIRMATION_NOT_RECEIVED` (the code is Proposed). The market sets no provider: Billpay asks Amex Pay with Bank Transfer for every link, and it picks the market's provider. The redirect link itself lasts about 10 minutes |
| Instrument statuses per journey context | `ReadBillpayInstruments.v1` | Which enrolled instruments the payment page may offer for each journey context the channel passes: `enrolledInstrumentStatuses`, with a list of statuses for `ONE_TIME_DIRECT_DEBIT` and one for `RECURRING_DIRECT_DEBIT`, set in each account type's release. `ACTIVE` alone for both unless the market sets it. DE, for example, can let Autopay take an instrument still pending verification while a one-time direct debit takes `ACTIVE` ones only. The key's name is Proposed |
| Pending sweep age | One-Data's hourly sweep | How old a pending entry must be before the sweep asks billpay-online about it: `pendingSweepAfter`, 2 hours unless the market sets it. Set it past the market's bank wait, so payments still waiting aren't reported. The name is Proposed, and how One-Data reads it is open |
| Card provider and authentication window | RequestConfirmation, Verify's card authorization check, and the waiting workflow's timer | Which provider runs a debit card's 3D Secure and authorizes the payment: Checkout.com in the UK; other markets' providers will be added over time. The authentication window is 2 minutes: a debit card payment whose callback hasn't come once the window and a 10-second grace have passed is cancelled by its own workflow, and no money has moved |
| Verification rule settings | The verification rules in Verify, Reverify and Represent, and `ReadBillpayInstruments.v1` | The limits the rules check a payment against, such as the largest payment the market takes and the instrument types it accepts. The Router passes them to the workflow in the resolved profile, so a payment keeps the values it started with. billpay-online also filters the instruments it returns to the payment page by the market's rules, so the page only offers what this payment can use |
| Scheduling horizon (Proposed) | The verification rules | How many days ahead a customer can schedule a payment: 30 by default. Verify declines a create dated beyond it. The payment page now takes its dates from `ReadPaymentOptions.v1`, for each customer, so whether this setting stays is open |
| Pay with MR Points (Proposed) | The Router | Whether customers in this market can pay with their Membership Rewards points. Off by default. With it off, the Router turns away a create that carries them with 422; how the page learns not to offer them is open. Points pay today only, whatever this setting says |
| Expected volumes | The governor's floors and budgets | How much execution work to plan for |
| BOTH rules, per behavior | The Router | Which journeys get Y for a behavior set to BOTH; for bank confirmation, which payment methods |

## Why some of these matter more than they look

The cancellation window and the execution time have to agree. The window must close before the dispatcher starts executing, so a cancel and an execution never race for the same payment. If they ever did, the guarded update would still let only one win, but the customer would see a 409 they didn't expect.

The cutoff decides how the governor treats a market. A SEPA market with a three-hour cutoff gets a floor rate, the remaining payments divided by the time left minus 30 minutes, so its run aims to finish half an hour before the cutoff. Online traffic usually comes first: if online response times or the shared Oracle degrade, every offline class is cut. A SEPA run is the exception. Online response times never cut it below its floor, and if online traffic would take too much of a downstream, online calls to it are capped until the cutoff ([When the cutoff wins](../design/throttling.md#when-the-cutoff-wins)). Oracle trouble still cuts the run, and the cutoff alert fires when it falls behind. The US has no cutoff, and its execution gets a fixed floor of 50 TPS instead. The [governor](../design/pacing.md#the-governor) explains how the floors are handed out.

Raven messages are the one setting with two levels. A market can change the default list, and an account type can change its market's. The two disagree when the Market Onboarding UI holds both: if the US turns the `SCHEDULED` message off for the whole market and US Corporate turns it back on, a US corporate payment follows US Corporate, because the account type's setting wins. A US consumer payment follows the market's setting, since US Consumer has none of its own.

Daylight saving deserves a test of its own: run the market's Schedules through both transition weekends before it goes live. The US needs no such test, since Phoenix time doesn't change. Execution runs every day, holidays included, so no market keeps a holiday calendar.
